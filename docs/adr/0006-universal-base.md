# ADR-0006: O2O 万能底座（六层防御圈）——设计哲学定稿与融合蓝图
日期：2026-08-13
状态：Accepted（作为融合期架构定稿；各模块落地单独排期）

## Context

**现状问题**：项目（web `oto-spatial-web` + RN `mobile` + 共享后端）所有能力都
写死在单一业务（需求局/组局撮合）上——状态机、计价、分发、信用、风控全部内嵌
在该业务的字段与路由里。时间一长就脱离本质：新增业务形态（家政 / 交友 / 跑腿 /
拼单）必须复制代码、改字段、重写流程，底座能力无法复用。

**灵感来源**（2026-08-13 网聊定稿版）：RPG 火箭筒的设计哲学 → 平台迁移——
「万能底座（人到人的信任与交付基建） + 可插拔弹药（场景 SOP）」。核心哲学：

- **接口标准化**：发射管（订单状态机、清结算）口径不变，弹药（业务）随意换；
- **底层保守 + 上层激进**：底座逻辑极端稳定，业务参数极端可配；
- **向下兼容的生态**：新增业务只填「弹药属性表」，前端一行不改。

**全景图定稿**：22 个核心模块收拢为「六层防御圈」
（第一圈用户体验触达 / 第二圈通用业务核心 / 第三圈 AI 神经 / 第四圈生态网关 /
第五圈安全风控 / 第六圈基础设施生存）。本 ADR 将六圈落为项目融合期的架构骨架。

## Decision

### 二、融合顺序（本次定稿的关键决策）

1. **本 ADR 定稿蓝图**（即本文件，状态 Accepted）；← 现在的这一步
2. **融合本地两项目**（web + RN mobile + 共享后端）：按六圈切分——
   - `base/`（第二圈全部 + 圈① LBS + 圈③ gateway + 圈⑤ 可插拔风控）→ 共享层，
     两端复用，是「发射管」；
   - 业务侧只剩「弹药属性表」（圈① 动态表单配置 + 结算公式 + 风控勾选 + SOP 参数），
     前端按配置渲染，不写死业务字段；
   - 迁移路径：现状能力按上表逐圈「抽层」——先抽第二圈（已 🟢 的部分定义接口），
     再抽圈① 表单、圈⑤ 风控配置，🔴 模块不进本轮融合，立项单列。
3. **功能层迭代**（融合基线稳定后）：灵感漩涡等新玩法按「弹药」形态接入。

### 三、阶段建议（沿用网聊定稿）

- MVP/融合期：第二圈全部 + 圈① LBS/表单 + 圈③ 已有 LLM + 圈⑥ 降级兜底；
- A 轮前：全力第三圈 + 第五圈（不对称竞争优势）；🔴 模块里优先「AIGC 鉴真 +
  智能小法官 + 反欺诈探针」；
- B 轮后：第六圈生存层 + 多云多活 + 数据湖。

## Alternatives Rejected

- **继续单业务写死叠加功能**：新增业务靠复制代码，底座能力永不沉淀，越滚越发散，
  背离「底层保守、上层激进」哲学（本轮否决的核心动机）。
- **先融合项目再造底座**：融合后还要按新分层回炉重构一遍，等于两次结构性大变更，
  返工成本双倍；先定稿蓝图，融合时一次按层切分。
- **蓝图再压缩**（如砍掉第三圈 AI / 第五圈风控进 MVP）：与「底座 = 信任与交付基建」
  本质冲突——AI 神经与风控引信正是底座区别于普通 LBS 工具的核心，只做交易管道
  就没有护城河。

## Consequences

- `docs/PROJECT_STATUS.md` 同步本定稿；融合期任务按六圈分层排布，进度以
  圈/模块粒度更新。
- 融合后新增业务流程：后台填「弹药属性表」（表单字段 + 计价公式 + 风控勾选 +
  SOP 参数）→ 前端自动生成 → 复用底座状态机/清结算/信用/IM，前端一行不改。
- 六圈是长期架构契约：后续开发一律按圈归位，禁止把业务字段写进底座层；
  新模块落地前先定位到所属圈再立项。
- 🟢 模块的「接口定义」（状态机枚举、ledger 分录、计价公式 schema、风控引信表）
  是融合期第一阶段产出物，先定接口再搬代码。
