## 框架定稿（用户拍板汇总）

### 原则一 · 任务两分 + LLM 介入拆解（v3 核心新增）
**简单 / 复杂不是发起人自选，也不走平台规则——由 LLM 介入判断与拆解：**

1. 发起人用一句话描述需求（如"我要清理整个房间"——太笼统）
2. **LLM 介入**：把模糊描述拆成**相互独立的模块任务**（每模块 = 一个可独立验收的结果），输出标准化模块清单
3. **发起人确认**模块清单 → 可增删、可改描述，**接单之前全程可增删/取消**
4. 确认后成单 → 接单后模块**不可增删**（防止骚扰混入）；只能补说明，不能改验收点
5. **复杂任务最低 2 个模块**（用户拍板）；拆出 1 个或拆不动 = 简单任务 → 结果导向单点验收

```
完成一个"分阶段验收确认的闭环"：
  一句话需求 → [LLM 拆解] → 模块清单草案 → [发起人增删确认/取消]
  → 发布广播 → 接单 → 逐模块验收（响应者申报 → 需求方单模块确认）
  → 全部确认 → 放全款 · 争议只对出错模块开
```

### 原则二 · 争议处理：原因拆分优先 + 自动流程与协商相辅相成（v3 修正）
- **拆原因不拆金额**：平台判"这单为什么不对"，不判"值多少"。
- **自动流程 + 双方协商 = 相辅相成**（用户拍板，不是二选一）：
  投诉 → 自动按原因映射金额规则处理（C3）→ 响应者 48h 可申诉 → **协商流程介入**（双方可自动结果之上谈，Fiverr Resolution 模型）→ 达不成回到自动判责。
- 公开原则：判责记录 `DisputeRecord` 全程留痕，UI 可查。

## 对标基准（2026-08-06 实查，国内外 6 家）

### 国外
| 平台 | 验收/放款 | 质量不达标处理 | 关键数字 |
|------|-----------|---------------|---------|
| **Airtasker**（澳，1:1 任务主范本）| 托管 Stripe；响应者申报完成 → 需求方验收后放款（已被我们抄为 requestPayment 闸）| **无自动扣费档位**；不满意 → 双方协商 → 平台介入（钱留 escrow 直到定论）| 服务费 12.5–20%（响应者承担）· 需求方 30 天不验收自动取消退款 · 取消费封顶下次提现 50% |
| **TaskRabbit**（美）| Tasker 发票 → 客户支付；随单 | 差评+客服介入；**无按比例扣款** | 24h 内取消 = 1 小时工时费补偿 · no-show = 1 小时费 |
| **Fiverr**（跨国，数字服务）| escrow，交付 → 客户确认；不确认 3 天自动放款 | **唯一有"部分退款"的平台**：Resolution Center 协商，**上限 60% 订单价**、最低 $5、仅服务方可发起、一单一笔 | 部分退款不影响服务方绩效指标（特意这么设计的） |

### 国内
| 平台 | 验收/放款 | 质量不达标处理 | 关键数字 |
|------|-----------|---------------|---------|
| **美团闪购/外卖** | 平台托管；确认收货后结算 | **履约异常自动退款**（缺货/少送/超时等 12 类场景平台自动判） | 自动退款条件：订单 ≤¥500、用户每月至多 2 次；异常单 **全额退**，无按比例 |
| **天鹅到家**（58 系家政）| 上门后结工资 | **黑点案例**：靠"14 天不退费"格式条款，被消保委/媒体广泛批评"霸王条款"；无质量扣费 | 首次匹配费 1000–1500 元不退 · 上户满 14 天服务费全不退 |
| **京东服务+ / 淘宝服务市场** | 服务完成 → 确认 | 申诉→平台介入判责；判责即全额退或全不退 | 无按比例扣费 |

### 对标结论（关键认知修正）
1. **业内没有"质量分级扣单子金额比例"的机制**。全部是二元：全额放款 / 全额退款（+ 平台介入仲裁判责归属）。我上一版 D2 的"10%/30%"档位是**拍脑袋，删掉**。
2. **"部分退款"只有 Fiverr 有**，且机制是：协商制（服务方发起）上限 60%、一单一笔——不是平台定档，是**双方谈**。
3. 平台责任边界：**判责（钱归谁）由平台管，金额协商（退多少）由双方管**。Airtasker/TaskRabbit/Fiverr 一致。
4. 国内"自动全额退"门槛普遍（美团 ≤500 元小额单自动退），暗示**小额单应走自动路径，大额单留协商窗口**。
5. 天鹅到家是反面教材：格式条款硬性不退 → 大规模投诉/舆论反噬。**我们应避免"取消不退/质量不退"的绝对条款**（注意：我们已有一个——发布费不退，但那是明确对价，可解释；服务金额的绝对不退需要理由）。

## 决策记录（已拍板 ✅ / 待你确认 ⏳）

### 第一部分 · 两套验收模型（含 LLM 拆解）

**M1 ✅ · LLM 拆解任务**（用户拍板）
- 发布时一句话描述 → LLM 介入拆解为独立模块 → 发起人确认
- LLM 不可用（无 key/超时）→ 降级：mock 规则拆解（复用 cluster 的 mock 先例）或手动拆分
- 拆不出模块 / 只有 1 模块 → 按简单任务（结果导向单点验收）

**M2 ✅ · 简单任务验收（结果导向）**
- 复用现有 fulfilment.ts：响应者申报"结果达成"（马桶通了）→ 需求方确认 → 放款

**M3 ✅ · 复杂任务模块化确认**
- LLM 拆 2-N 模块，每模块：名称 + 验收标准文案（LLM 生成，发起人可改）
- 接单前：发起人可增删模块 / 改文案 / 取消 —— 全程自由
- 接单后：模块不可增删（只可补说明）—— 防"外包混入"
- 每模块独立状态机：未开始 → 响应者申报 → 需求方单独确认 → 确认数 +1
- 全部确认 → 放全款；未确认模块 → 冻结可退

**M4 ✅ · 复杂任务与 fulfilment 状态机（独立，用户拍板）**
- 新建独立 `moduleFulfilment` 记录；简单任务保留原单点 `fulfilment`，互不污染
- 复杂任务完全走模块链路（模块申报 → 模块确认），不进入原 fulfilment 单点

**M5 ✅ · 模块金额 = LLM 建议权重（不等分，用户拍板）**
- LLM 拆解模块时**同时给出每模块建议价格**（如"粉刷墙 60% + 清垃圾 40%"）
- 拆解结果（模块清单 + 建议价格）**一起给发起人确认**，可改
- 金额绑定按确认后的权重 → 争议按出错模块权重折退
- LLM 不可用降级时：等分兜底（标记"默认等分，可改"）

### 第二部分 · 争议处理：原因拆分 + 自动/协商相辅相成

**C1 ✅ · 原因官方分类**（6 类，用户默认通过，可增删）
| 原因 | 说明 | 判责倾向 |
|------|------|---------|
| no-show 未到场 | 无服务发生 | 响应者怠 = 全退 |
| 迟到/早退 | 履约但时效违约 | 响应者部分责任 → 协商部分退 |
| 结果/模块不符 | 做了但没达到验收标准 | 全退或按模块整退 |
| 交付物缺失/损坏 | 东西没给到位 | 响应者怠 = 全退 |
| 需求方变更/取消 | 需求方改主意 | 已发生成本响应者获补偿 |
| 不可抗力/模糊 | 说不清 | 平台介入判责 |

**C2 ✅ · 判责流程 = 自动 + 协商相辅相成**（用户拍板）
```
需求方选原因 + 凭证 → [自动流程：按原因映射金额规则处理]
→ 响应者 48h 申诉 → [协商流程介入：双方在自动结果之上谈（Fiverr Resolution）]
→ 达成 → 按协商结算 · 不达成 → 回自动判责终局
```

**C3 ✅ · 金额处理与原因绑定**
| 原因判定 | 金额处理 | 对标 |
|---------|---------|------|
| 响应者全责（no-show / 交付物缺失） | 全退需求方（escrow 返回）| Airtasker |
| 响应者部分责任（迟到/部分不符） | 协商部分退款（上限 60%，一单一笔）| Fiverr |
| 需求方责任（变更/取消） | 已付部分归响应方（补偿已发生成本）| Airtasker 取消费 |
| 双方对等/不可抗力 | 协商均摊或互认 | — |

**C4 ✅ · 举证与公开原则**
- 投诉必选 1 条凭证（文字，MVP 无图）→ 响应方 48h 回应 → 超时默认按需求方判
- `DisputeRecord`：{ claimId, reason, appeal, decidedBy, note, at } 全程留痕，UI 可查
- 争议中订单资金冻结，判责后放款/退回

- **判"响应者部分责任"**（迟到 / 部分不符）→ 按责任占比降信用（比全责轻，占多少降多少）
- **判"需求方责任"**（变更/取消）→ 需求方惩戒：失信标记 + 下次发布费加成（占比对应）
- "对错"与"责任占比"双轨：全责一档、部分责按占比一档
